# Merge Build Order

## Phase 0 — Freeze architecture, not development

- Keep the current 71 agents and 13 workstreams.
- Add project-2 domain leaders and capabilities to a consolidation manifest.
- Choose one backend/control plane: Project 1.
- Choose one UI runtime: existing `apps/web`; port Project 2 surfaces into it.

## Phase 1 — Canonical contracts

- canonical organization/user/tenant context
- company/profile/brand
- account/contact/lead/opportunity/customer
- strategy/campaign/content/creative/SEO
- workflow/task/approval/handoff/artifact
- agent/capability/tool/prompt/evaluation
- memory/document/citation
- metric/experiment/recommendation/outcome
- billing/entitlement/usage/audit

## Phase 2 — Merge intelligence

- merge 14 project-2 domain leaders into the existing specialist workforce
- implement Marketing Commander
- add capability ownership contracts
- add unified context builder
- add evidence/provenance

## Phase 3 — Merge execution

- merge automation model
- merge workflow catalog
- merge tool permission model
- add durable execution behind existing workflow contracts
- connect approvals to external side effects

## Phase 4 — Merge knowledge + memory

- RAG
- document ingestion
- source citations
- company/account/campaign/interaction memory
- learning memory

## Phase 5 — Product

- client portal screens
- command center
- admin
- CRM
- campaign/content/SEO/analytics surfaces
- billing/entitlements

## Phase 6 — Outcome loop

- attribution
- CAC/pipeline/revenue/profitability
- experimentation
- recommendations
- autonomous optimization under policy

## Phase 7 — Hardening

- tenant isolation
- security tests
- agent evaluation
- integration contracts
- background jobs
- deployment
- observability
- backup/restore
- licensing/provenance

## Segmentation rule

Do NOT fork the architecture by segment. Only after the universal product is functional should packaging/customization introduce segment-specific limits, integrations, governance, deployment options, pricing, and workflows.
